## Product and architecture

Badminton event software for registration and shirt/payment administration, division/pool organization, match generation, umpire scoring, court dispatch, result validation, tournament progress, public spectators, projection and paper scorecards. Singles, standard doubles pairing and team rosters are supported. There is one tournament state per deployment, not a general multi-event database.

The app is React 19.3.1 / TypeScript 5.9.3. Next 16.2.6-style App Router files run through Vinext 1.3.0 / Vite 8.0.13 and the Cloudflare Vite plugin. Tailwind 4/PostCSS, custom CSS and Phosphor icons provide styling. Worker code routes static assets, image optimization and API requests. Production builds into `dist/client` and `dist/server`. The generated `.vinext` directory is ignored; obsolete tracked Geist font caches were removed during the reliability upgrade.

| Area | Source and responsibility |
| --- | --- |
| Main client | `app/page.tsx`: registration wizard, staff role/navigation state, organizer controls, client saves and umpire queue |
| Tournament domain | `lib/tournament.ts`: types, hydration, registration-derived entries, draws, scores, rankings, medals, schedule |
| Court operations | `lib/game-day.ts`, `lib/staff-events.ts`, desk/help components |
| State API | `app/api/state/route.ts`: direct prepared D1 SQL, auth, mutation and revision locking |
| Payments | `lib/payment-proof-server.ts`, payment API routes/components: R2 receipts/QR and separate D1 payment settings |
| Runtime protection | `worker/index.ts`, `lib/request-security.ts` |
| Displays and print | Projector, countdown, next-game and print components; `app/globals.css` |
| Persistence metadata | `db/`, `drizzle/`; initial migration describes tournament state, additional runtime tables are created by handlers |
| Demo / validation | `preview/`, `vite.preview.config.ts`, `tests/`, `design-qa.md` |

D1 `tournament_state` stores a single JSON payload at ID `racketeers`, with revision and timestamp. The model includes phase, theme, name/venue/date/time/courts, divisions, registrations, matches, medal points, staff help/events and Game Day settings. Payment text is separately stored in `payment_settings`; rate limits use `request_limits`. Sponsor metadata uses a separate lazily created `sponsor_images` table; R2 holds images. API writes use revision-conditioned UPDATEs to avoid simultaneous whole-state overwrites. This architecture has shared-state concurrency and payload-size limits, not row-per-match isolation.

Organizer edits debounce at 2.5 seconds. On 409 the client pauses autosave, retains the complete local draft and shows the affected sections. The organizer can download the private draft, then load the latest authorized state and reapply intended edits. There is no automatic merge or retry of a stale snapshot at a newer revision. Umpire scoring accumulates local taps, debounces at one second and serializes PATCH requests. It keeps failed snapshots for retry and warns before leaving unsaved work, but has no persistent offline storage. Visible-page polling is one second for unlocked organizers, two seconds for spectators/projector, otherwise 60 seconds; an open umpire scorecard suppresses full state polling. Staff signals poll separately each second without replacing queued scores or unsaved setup. Sync labels are Saved/Saving/Offline concepts, not proof of offline persistence.

## Registration, identities, shirts and contacts

Registration uses three visible steps: Division & players, Entries & shirts, and Review & payment, with focus/scroll changes between steps. The event details, rules and separate disclaimer/waiver links stay in the desktop left sidebar and above the form on narrow screens. Division selection and player details share the first step; shirts move to the second. Division changes preserve player drafts, including Player 2; singles submissions exclude hidden partner fields. Doubles requires both names. Every new participating player needs a club/group, Facebook profile URL and phone/mobile. Valid Facebook hosts are facebook.com, www/m/mbasic.facebook.com, HTTPS, non-root profile path and no embedded credentials. Phone accepts common punctuation and 7–15 digits without enforcing a single country. Public level selection was removed; new registration player/desired levels are blank, while organizer level overrides and legacy/custom level fields remain.

Registrations are individual player records. Doubles partners point to each other; derived entry IDs use sorted registration IDs. Singles produces one entry per registration. Team mode groups registrations by trimmed team name (or Unassigned Team). Registration-managed divisions remain empty after final-player removal. Creating/duplicating a division does not invent player registrations. Player contacts synchronize across linked entries via `personId || id`; names remain visible in matchups while contacts stay out of public state.

Players can have at most two linked entries, in the same or another division, with the same or a different partner. Combined second entries first require an explicit Who is entering again choice between the two original named players; singles offers only its participating player. The second-entry form derives the selected person's contacts from the first entry and keeps each person's alternative draft and shirt choices separate. Same partner means the other original player, so choosing Player 2 reverses the owner/partner relationship. The API derives identities server-side using secondEntry.owner (primary or partner); omission defaults to primary for compatibility, while malformed or ineligible choices reject atomically. Combined and later linked doubles/team second entries also require an explicit, initially unselected Same partner or Different partner choice. New partner fields appear only after Different partner is selected; switching choices keeps alternate partner drafts separate from the first entry. A second entry requires a black-shirt or second-tournament-shirt choice; the reused partner also gets a choice. Each player has their own shirt size. Two entries submitted together share the generated registration edit PIN and payment group. Adding an entry later creates a fresh PIN for the new entry while retaining linked identity/payment group. A pair's partner record can rely on the primary record's PIN rather than its own hash. Do not interpret every player record as an independently PIN-owned account.

Registration IDs are server-generated `REG` plus uppercase UUID without separators (35 alphanumeric characters), collision checked; supplied public IDs are ignored. Legacy IDs are preserved. Eight-digit edit PINs use cryptographic random rejection sampling. Confirmation tells the player to save the ID and PIN. PIN lookup exposes only editable owned registration data, with partner contact and entry-count details. Self edits preserve organizer payment/shirt confirmation and classification controls rather than accepting arbitrary protected fields.

Organizer Registration includes Add Player using the same form, paid confirmation, shirt receipt, pair assignment, player contact edits, payment proof controls, PIN recovery/replacement, division filtering and exports. Moving a reciprocal doubles pair into another doubles division keeps their records/payment references but clears matches/scores/schedules in both affected divisions and resets pool override after confirmation. Scoped registration reset requires organizer access, `RESET`, current revision and unlocked phase; it removes affected registrations and matches while keeping division settings and other divisions. It does not delete R2 files.

Shirt chart is `public/shirt-size-guide.webp`, with a zoomable 100–300% dialog and full-size image link. XXL corresponds to 2XL in the form. Units were not specified in the supplied chart; 3XL measurements require organizer input.

## Payments and exports

Payment provider/account number/account name/instructions are public registration instructions stored independently of tournament JSON. Account number is text to preserve leading zeroes. QR is `payment-instructions/qr.png` in private R2, intentionally public through the settings API. Text and image save are separate operations and can partially succeed.

Proof upload is optional and does not confirm payment. Organizer must explicitly confirm each covered individual player; confirmation is reversible. PNG/JPEG/WebP inputs up to 2 MiB convert client-side to PNG with longest side at most 2000px; converted output is also capped. Server requires PNG headers/end markers, bounded streamed size and positive dimensions <=24 million pixels. These checks are not a complete image decoder. Authenticated previews use blobs rather than an image proxy.

Current receipt keys use `payments/groups/<paymentGroupId>/<paymentGroupId>.png`; legacy reciprocal pairs use sorted-ID paths under `payments/pairs/`; older individual keys use `payments/<registrationId>.png`. Reads check current and compatible legacy keys and prefer newest upload. Linked players/entries share proof ownership. Organizer can upload/replace and delete; public owner upload/replacement is locked outside Registration. Deletion removes the linked known keys while retaining registrations/payment confirmations. Removal of a registration prevents normal retrieval through that record but does not remove stored objects.

Exports include player name, ID, phone, Facebook, club, partner, division, shirt size, payment status, proof link and saved receipt-review fields. Group amounts repeat on linked player rows and must be deduplicated by payment group before totaling. XLSX can include all divisions on uniquely named sheets; CSV requires one selected division. CSV guards spreadsheet formula-leading values; XLSX stores text as inline strings. Export proof links are read-only bearer URLs signed with HMAC using the current organizer hash, valid for seven days; organizer PIN rotation invalidates them. They permit receipt viewing without entering a PIN, so keep exports private. Exports are administration lists, not complete backups. Setup provides a private exact tournament-state recovery download, but no production restore/import UI. Payment settings, raw receipt-review rows, sponsor metadata and R2 objects require separate backup; see [Backup and recovery](docs/backup-recovery.md).

## Tournament formats, pools and seeding

Divisions independently choose singles/doubles/team, group format, championship format and group/championship scoring. Pools honor valid explicit zero-based overrides and then balance unassigned entries into the smallest pool. Labels are Bracket A, B, etc. Pool generation bounds pool count to entry count, but ranking uses configured pool count; empty pools and small rosters need coverage.

Group formats: round robin generates each pair once; double round robin repeats with reversed sides; custom generates the requested cyclic matchup count; `single_elimination` currently creates one opening regular pairing round. It is not itself a complete automatic knockout progression. Championship ladderized mode creates rounds for 2/4/8/16/32/64 down to the final and bronze when size >=4. Semifinals/final seeds 1 v 4 and 2 v 3, then winners to gold and losers to bronze. Direct medals puts ranked 1/2 in gold/silver and 3/4 in bronze.

One-pool championship ranking uses standings order; multiple pools interleave first places, then second places, etc., up to configured qualifiers per pool. Ladder first-round seeding uses high/low rank pairing with a fallback when rank lists are shorter. Subsequent rounds use validated winners or one-sided byes. Final/bronze helpers retain their existing provisional seeding from completed played semifinals, while forfeited semifinal results now require validation before supplying a winner. Ladder advancement uses validated winners or byes. Game Day eligibility requires earlier results validated in either case.

Automatic reseeding only edits untouched ready matches with no points/completed sets/validation, dispatch reservation, hold or forfeiture. Manual championship mode skips automatic reseeding. Validation invokes reseeding. Starting a game locks its entrants against automatic rewriting. Regeneration replaces all matches and their IDs/PINs/scores/schedules; it must not happen as incidental hydration or a cosmetic edit. Hydration migrates legacy registration-linked entries only before v5, expands typed partners, preserves old IDs and repairs missing/duplicate four-digit match PINs. Legacy placeholder entries without registration IDs are not recovered as registrations.

## Scoring and ranking rules

Match formats are `single_31`, `single_21`, `best_of_3_21`. Default regular rule is 31, win by two, cap 35; default 21/championship rule is 21, cap 30. Per-stage overrides cover regular, rounds 64/32/16, quarterfinal, semifinal, gold and bronze. Target normalizes to 1–99; cap to at least target and at most 199. Both legacy `win_by_two` and `capped_win_by_two` normalize to capped mode; `first_to_target` ends at target without a two-point lead.

In capped mode score controls slide to `min(cap, max(target, opponent + 2))`. A set wins with an unequal score at/above target and two-point lead, or an unequal score at cap. Examples: 31–30 is not complete, 32–30 is legal, 35–34 wins at the cap; 35–35 is invalid. Once a score is winning, additions stop; subtraction can correct it before explicit completion. Completed sets stay locked until explicitly reopened. PATCH enforces numeric/legal bounds on the server as well as client controls.

Winning points alone are not a completed set. Single-set matches need one completed legal set; best-of-three needs two. A forfeiture supplies a separate match winner and official awarded sets, while recorded play sets remain intact. Umpire completion shows Game complete / Awaiting organizer validation. Organizer validation marks finished/validated, completes legal winning sets for played results, clears court and reseeds. Unvalidation retains scores and clears court, setting played results live while forfeited results remain finished until the forfeiture is cleared. Validated games cannot be scored or opened for umpire editing.

Standings include validated regular matches only. Played/wins/losses and summed set points produce point difference. Sort is wins descending, difference descending, points for descending, then alphabetical display name. No head-to-head tiebreak exists. Medal result helpers require validated gold/bronze games and use tournament medal point settings.
